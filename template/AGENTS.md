## 协作协议(架构师 + 突击手)
- **触发词 `/duo`**:默认情况下 Codex 自己直接完成任务(读写代码、测试),不创建任务单。仅当用户消息含 `/duo` 才进入协作模式:
  - `/duo 执行 <编号>`:Codex 担任突击手,执行已有任务单。优先匹配执行、验收、状态子命令,其余参数才作为新需求;缺少编号时先澄清。
  - `/duo <需求>`:Codex 担任架构师,只规划不实现,写任务单到 `.work/tasks/`,然后提示用户让 Cursor 或另一个 Codex 聊天执行。
  - `/duo 验收 <编号>`:Codex 验收指定任务单。
  - `/duo 状态`:Codex 汇总所有任务单状态。
  - 未出现 `/duo` 时,不得创建任务单,也不得拒绝写代码。
- 角色由当前消息决定,不与工具绑定。架构师与突击手建议使用不同聊天,通过文件交接。
- 架构师(Codex):只规划与验收。复制 `.work/tasks/000-template.md` 创建小任务,填写目标、允许文件、禁区、验收场景与验收命令;场景需描述输入/操作及预期结果,覆盖正常、异常和必要回归。
- 交接只靠 `.work/` 文件和 Git,不依赖聊天记录。建议每个任务独立分支或 worktree。
- 状态流转:待办 → 进行中 → 待验收 → 完成;验收不过退回进行中,仅架构师可置为完成。

## 突击手执行流程
1. 先读项目根目录 `AGENTS.md`、`.work/plan.md`、`.work/notes.md`,再按编号查找 `.work/tasks/NNN-*.md`。一次只执行一个任务单;编号缺失、匹配不唯一或任务不存在时先澄清;不得执行 `000-template.md`。若没有 `.work/`,提示先运行 `duo-init`。
2. 只执行「待办」或「进行中」任务;「待验收」或「完成」不重复执行,提示验收或明确重新打开。开始时把「待办」改为「进行中」;已有「进行中」任务继续执行。
3. 首次执行前填写「代码版本」:工作目录、分支(或 detached HEAD)、`git rev-parse HEAD` 得到的基础提交。用 `git status --short --untracked-files=all`、`git diff`、`git diff --cached` 记录已有改动及新增文件,区分本任务与既有工作;有重叠且无法区分时先澄清。继续执行不得用当前 HEAD 覆盖原基础提交。
4. 只改「允许改动文件」,不碰「禁区」;额外允许更新当前任务单的「代码版本」「状态」「备注」和 `.work/notes.md`。不扩大范围、不顺手重构。范围外发现追加到 `.work/notes.md`,注明位置与现象。验收场景或允许范围不足时交回架构师补充,不得自行放宽标准。
5. 实现后亲自运行「验收命令」并逐项验证「验收场景」,在备注记录实际命令、结果及场景证据。命令通过但场景不满足不算完成。失败则在允许范围内修复;无法通过时保持「进行中」并说明原因。
6. 自测通过后填写「代码版本」中的交接 HEAD、本任务提交(如有)、未提交文件清单及状态。对本任务仍未提交的代码文件记录内容 SHA-256,删除文件注明删除,新增文件也须包含;不对持续更新的任务单及备注文件计算自引用哈希。不自动提交、暂存、清理或覆盖用户改动。
7. 改为「待验收」并停止,提示回到架构师聊天发送 `/duo 验收 <编号>`。不得自行改为「完成」,不得在执行流程中顺便验收。

## 验收流程
1. 先读项目规范、计划、备注及唯一匹配的任务单,不验收 `000-template.md`;只验收「待验收」任务。核对「代码版本」中的工作目录、分支、基础提交和交接 HEAD,以及未提交代码文件的 SHA-256/删除状态。若代码在交接后变化、版本记录缺失或改动归属不清,先补齐或重新交接,不得宣称原版本验收通过,不得自动切换分支或重置工作区。
2. 检查全部改动:运行 `git status --short --untracked-files=all`、`git diff --cached`、`git diff`,逐个读取未跟踪文件。已提交改动还需用 `git diff <基础提交> <交接HEAD>` 检查(将占位符替换为记录的实际提交);不能仅看默认 `git diff`。与执行前记录比较,区分既有改动与本任务改动。
3. 核对范围:本任务只允许修改指定文件,以及任务单的版本、状态、备注和 `.work/notes.md`;检查是否碰了禁区。再核对 `.work/plan.md` 与 `AGENTS.md` 中的架构约束。
4. 在确认的交接代码上亲自运行全部「验收命令」并逐项验证「验收场景」,在备注记录实际命令、结果、场景证据及验收的代码版本。任一项不满足都不能置为完成。
5. 通过后状态改为「完成」;不通过则改回「进行中」,在备注写明具体问题。架构师如做极小修正,须记录改动、更新版本信息并重新验证受影响的命令和场景。
6. 处理 `.work/notes.md` 中的范围外发现:转成新任务或标记忽略。更新 `.work/plan.md` 的进度,给出下一张任务单。

## 无 Git 或旧任务单
- 有 Git 但没有初始提交时,基础提交写「无初始提交」,记录执行前文件清单及本任务涉及的已有文件 SHA-256;验收检查暂存、未暂存和未跟踪文件,不运行不存在的提交间 diff。
- 无 Git 时记录绝对工作目录、执行前文件清单及本任务涉及的已有文件 SHA-256;交接时记录变更清单、代码内容差异和结果文件 SHA-256/删除状态,验收逐项核对。无法还原改动范围时先补齐证据。
- 旧任务单缺少「验收场景」「代码版本」时由架构师先补充,不得编造历史基础版本;无法确定历史版本时记录现状并明确重新交接。
